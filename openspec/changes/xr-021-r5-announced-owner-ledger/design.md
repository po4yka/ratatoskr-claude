## Context

XR-021 CONTRACTS.md R5-06 is the source of truth. This file records the local decisions.

## Decisions

- The ledger row is written by `ArchiveOutbox::enqueue_with`, the one function every `ai_archive.*` fact passes through, so no fact can be enqueued without its row. The owner is the envelope tenant and the subject is `fact.aggregate()`: the archive id on `archive.imported`, the conversation and project ids, and the external artifact id (the aggregate is `artifact:<id>`). Tombstones and operation reports record nothing. `subject_id` is the local part of the aggregate, so an artifact whose provider id recurs keeps one row per owner, exactly as the aggregate does.
- `account_id` is read from the `exports` row of the archive the fact names, in the same statement, and stays null when no export row exists. The ledger has no foreign key, so no export or account deletion cascades it. A later fact for the same `(subject, owner)` keeps the row and refreshes `ai_archive_id` to the archive that fact names (`on conflict do update`, the one deviation from the contract's `do nothing`, and it changes no key or owner), so a survivor announced again under a retained archive moves its row off the archive a deletion tombstones, and the rows still naming a tombstoned archive after the survivors were announced are exactly the ones Knowledge dropped.
- A tombstone for the pair `(subject, owner)` names, as its `ai_archive_id`, the earliest archive the request deletes that observed the subject and whose own archive row is announced to that owner; when none is, the earliest deleted archive that observed it; when none, the first deleted archive. The owner is read from the ledger only, restricted to the request's accounts so a recurring artifact id never reaches another account's owner.
- The outbox rows a tenant-scope deletion removes are those whose tenant is an owner the account's ledger rows name, except tombstones that are still unacknowledged (R5-11), so the removal no longer needs the request's tenant reference. The facts of a conversation, project or archive scope are found by aggregate identity, which is a UUID and needs no tenant filter; only the Artifact facts keep the owner filter, because a provider artifact id recurs across tenants.
- The survivor path takes the owner from the retained archive's latest `archive` ledger row. A retained archive with no ledger row was never announced, so its survivors announce nothing; Knowledge holds nothing for it to repair.
- `PlatformUsers` keeps its import-time use: `ImportProjection::publish` chooses the owner a new fact carries. `reparse.rs::privacy_blocked` looks for unfinished requests under the account id alone, because a request is now recorded under the supplied account reference.
- Ledger rows of a tombstoned subject are deleted in phase A after the tombstone rows are built; the rows of an account's archives go with the archive tombstone, and a tenant-scope deletion deletes every row of the account's `account_id`.
- Known limitation, recorded by the XR-021 round 5 review fixes: the key is `(subject_kind, subject_id, owner_ref)` and `account_id` is overwritten by the latest announcement, so a provider Artifact id that two accounts announce under one Platform owner (which a mapping change can cause) keeps only the last announcing account. A deletion of the earlier account then finds no ledger owner for that subject and emits no tombstone for it. This is a deviation from the contract's one row per subject and owner, and it is the same class as the open artifact-id reuse of R5-15; keying `account_id` into the primary key is not done, because a tombstone is addressed per `(subject, owner)` and the two accounts would still share it.
