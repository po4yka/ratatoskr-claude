## Context

XR-021 CONTRACTS.md is the single source of truth for every cross-repository contract. This change implements its Claude half and records only decisions local to this repository.

## Decisions

- The capability route is mounted on the same sub-router as the receipt route in `receipt_router`, under the `no_store` layer, so the capability is advertised exactly while the receipt works. A static fault table in `fault.rs` renders every refusal as an `ErrorEnvelope`; the receipt route is `post(...)` with a method fallback for 405. Diagnostics are logged once at the boundary and never enter the envelope.
- The incomplete-import warning is built only by `platform_receipt::incomplete_import_warning()` and `OperationReported::validate()` is the test oracle (S06 D3).
- The Platform user is not stored in the Claude database. The `claude_archive` account id is the archive identity and the configured `platform_accounts` mapping (Platform user, account) is the only link. The work order says the import plan's tenant id is the Platform user; the code says it is the account id, so facts and tombstones resolve the owner by reverse lookup of that mapping, supplied as a constructor parameter and never a global. An account with no mapping emits no `ai_archive.*` fact (operation reports still flow) and the import records the skip in the log by safe class.
- Privacy deletion keeps `tenant_ref` as the request scope identity and requires it to be `user:<Platform user uuid>` only when the inventory has tombstone subjects. The operator command resolves the archive account to that reference through the same mapping before planning.
- The generic pump selects unpublished rows of the closed event-type list ordered by `occurred_at, event_id` and publishes the stored envelope unchanged with `Nats-Msg-Id` equal to the row's `event_id`. An event type outside the closed list is a hard error; the schema `CHECK` makes such a row impossible to insert.
- New code lives in new files (`planning_closure.rs`, `rows.rs`, `tombstones.rs`, `contract_projection.rs`, `fault.rs`) because `planning.rs` and `execution.rs` already sit near the size limits.
- Deletion order is rows first, bytes second, complete last. Phase A deletes the scope rows and the dependents, recomputes blob sharing against the rows that remain, inserts tombstones and records `rows_removed_at` and the evidence blob key in one transaction under the tenant lock. Phase B erases bytes and marks items purged. Phase C writes the audit and completes the request. `finalizing` is no longer written.
- Facts are enqueued one by one with `ArchiveOutbox::enqueue_in`, not with `publish_import_in`. That function requires every subject's provenance to equal the import head, but a fact's provenance names the parser release that last wrote its entity, which is what the contract's own provenance check needs, and after a reparse that rewrote only some rows the two differ. Each project, conversation and Artifact row therefore carries the parser stamp of the release that wrote it, and a reparse that reads unchanged content leaves the row, its stamp and so its digest alone.
- A subject is `added` when no earlier fact exists for its identity, `updated` when the current record differs from the latest earlier fact, and absent when equal. Equality is on the whole record, not on `content_digest` alone, because a title change does not change the digest of the messages but is still a change Knowledge must see.
- The initial import now persists what the facts need: project description and instructions, conversation project link and provider time, message order, time and parser stamp, and the reconciled Artifacts with their versions. Artifacts are observed by their export so scoped deletion finds them.
- The legacy `claude.subject.reparsed.v1` outbox row is gone: it was not a contract event, and the schema now lists the closed set of types.
- Children inherit the removal of their parent in the deletion closure, including a child that another retained export also observed, because the parent row cannot be deleted while a child still references it. A retained message whose parent is removed has its parent reference cleared.
- Deletion locks both the tenant reference and the archive account id: imports lock by account, and the tenant reference is now the Platform user, so locking only the reference would let a deletion race an import.
- The operator command resolves the archive account to the Platform user reference through the configured mapping before planning, and resolves blob lengths from the blob store (`BlobStore::locate`) because the inventory stores keys, not lengths.
- The projection is verified only against the synthetic export schema. The parser is bound to that schema, so no claim is made about real Claude exports.

- The service binds two loopback listeners, because S05 allocates 8097 to the receipt and 9086 to the operator plane. `admin_router` serves only the operator routes and `receipt_router` only the receipt and capability routes, so a default deployment is reachable where Platform forwards to and the operator plane is never served on the receipt port. `RATATOSKR__RECEIPT__LISTEN_ADDRESS` defaults to `127.0.0.1:8097`, must be loopback, and must differ from the operator address.
- A subject the projection cannot announce is counted and named on the head as a gap (`unprojected_project`, `unprojected_conversation`, `unprojected_artifact`), downgrades `complete` to `structurally_partial`, and is reason enough to re-announce the head on a reparse. The operation report of an import takes the same gaps and completeness.
- A reparse head is built from the export's first persisted completeness report, not from the reparse's own comparison, because the comparison only knows conversations.
- An Artifact carries its `account_id` and is identified by account, scope and provider id: unique indexes for message, conversation, project and unscoped Artifacts make a later export of the same account observe the existing row. Tenant-scope deletion and the portable export select Artifacts by that column.
- A deletion whose tenant reference is not a Platform user stays refused when it has a raw archive: the owner exists only in the account mapping, and an account that lost its mapping after facts were emitted holds data Knowledge still serves, so skipping the tombstone would leave it there. The tombstone envelopes carry the request correlation id exactly as the operator recorded it (`privacy-delete:<request id>`, which is a valid envelope reference); a stored value that is not a namespaced reference falls back to `privacy_request:<request id>` so execution cannot stall, and both are asserted.
- The added, updated or unchanged decision reads the latest earlier fact of the same tenant only (`tenant_ref` of the outbox row), because provider Artifact ids such as `react-component` recur across tenants. An Artifact lookup also matches the `conversation_ref` and `project_ref` of the fact, so two Artifacts that share an id are not each other's previous revision; a message-scoped Artifact carries the conversation of its message. Two Artifacts with one id in two messages of the same conversation still share a scope on the wire, which the contract cannot tell apart; the removal of an Artifact's unpublished facts at deletion matches the same scope (aggregate plus `conversation_ref` and `project_ref`), so it has the same limit.
- A deletion finds the Knowledge analysis links of a removed conversation or Artifact only among the archives of the exports it deletes, because a provider Artifact id recurs across tenants and the id alone would reach another tenant's links, inbox rows and tombstones.
- The Platform account mapping must be one to one: configuration refuses a user that appears twice and an account that appears twice, because the reverse lookup from an account to its owner would otherwise pick one user arbitrarily.
- A reparse persists the messages and parts of every conversation it adds or changes, through the same helper the first import uses, so the fact that announces a conversation carries its messages.
- A project whose name and provider id the contract cannot hold is counted as an `unprojected_project` gap like every other unprojectable subject, instead of failing the import into an endless retry.
- Deletion removes the `ai_archive.archive.imported.v1` head of every deleted export in every scope, because its `source_export` names bytes that are erased; the removal set names the archive aggregate beside the removed conversations, projects and Artifacts.
- `claude_archive.outbox_events` has an index on `(tenant_ref, aggregate_type, aggregate_id, occurred_at desc)` because every import reads the latest fact of every subject it projects.
- The crash proof also asserts that no surviving row references a missing blob at either commit point, and the foreign-key census fails on a handled entry that no longer exists.

## Risks

- A duplicate delivery of an already imported archive rebuilds its operation report from the persisted completeness report alone, so the report can count fewer gaps than the head that listed omissions.
- Deleting an account that has a raw archive and no Platform mapping is refused rather than skipped (see Decisions).
- Tombstones cover the deleted archive, every conversation and project the deletion removes (whether or not Knowledge linked it, because the import announced all of them), and the Knowledge-linked Artifacts. A conversation or project is tombstoned under the earliest deleted archive that observed it. A conversation, project or Artifact that stays because a retained export also observed it gets no tombstone of its own, but its facts were announced under the deleted archive's id (a later export that sees an unchanged record announces nothing), so the archive tombstone would make Knowledge drop what the deletion kept. The row-removal transaction therefore enqueues an `updated` fact for each such survivor whose latest fact names a deleted archive, with `import_provenance` naming the earliest retained observing export (by `received_at`, then export id) and stamped a millisecond after the tombstone so the pump publishes it afterwards. `a_subject_a_retained_export_holds_is_re_announced_under_the_earliest_such_export` pins it. A survivor whose latest fact already names a retained archive is left alone, and a survivor the projection cannot announce is not announced here either.
- A fact is stored whole in its envelope. A conversation whose fact exceeds the broker `max_payload` (1 MiB by default) is refused by the broker on every attempt: the pump backs the row off, flips publisher readiness false on each failing pass and never names the conversation as a gap, because the limit belongs to the deployed broker and is not known to the projection. The same limit already bounds the extractor Document event (CONTRACTS.md S05), where an oversized event dead-letters; a size-aware projection is a follow-up, not part of this change.
- A residual cross-tenant dedupe race on content-addressed blobs is narrowed, not closed (S07).
- Existing development databases must be recreated from the edited `schema.sql`; there are no migrations.
